# AnonLink — спецификация продукта

Документ описывает **что именно делает продукт** и **чем это подтверждается**. Он написан для
владельца проекта: здесь нет внутренностей, но есть честные границы — что работает, что работает
частично и что осознанно не сделано.

## Как читать

Каждая функция описана по одной схеме:

- **Сценарий** — что делает человек.
- **Ожидаемое поведение** — что при этом обязано произойти.
- **Интерфейс** — где это находится в приложении.
- **Сервер** — какое правило принимается на сервере (сервер всегда главнее клиента).
- **Данные** — что сохраняется в базе, а что нет.
- **Безопасность** — что этим нельзя злоупотребить.
- **Приёмка** — чем именно подтверждено (модульный тест, интеграционный тест, браузерный тест,
  либо «проверено вручную» / «не проверено»).

Технические детали устройства — в [ARCHITECTURE.md](ARCHITECTURE.md); статусы по требованиям —
в [COMPLIANCE.md](COMPLIANCE.md).

## Понятия

| Понятие | Значение |
| --- | --- |
| **Анонимная личность** | Запись, которая создаётся автоматически при первом открытии сайта. Не содержит имени, телефона, e-mail, адреса. |
| **User ID** | Публичный идентификатор личности, например `AL7KM3-9PQ2-XRZ4`. Это **не** пароль: по нему можно только предложить чат (если заявки разрешены). |
| **Псевдоним** | Вымышленное имя собеседника, действующее только внутри одного чата. |
| **Фильтры поиска** | Добровольные предпочтения: пол, возраст, место, язык собеседника. |
| **Данные о себе** | Добровольно указанные пол, год рождения, страна, город, регион, языки. Никем не проверяются и собеседнику не показываются. |
| **Смягчение (расширение поиска)** | Автоматическое снятие фильтров по одному, только с разрешения пользователя и с явным сообщением. |

## 1. Личность и User ID

**Сценарий.** Человек открывает сайт впервые. Регистрации нет.

**Ожидаемое поведение.** В тот же момент создаётся анонимная личность; на экране появляется её
User ID, кнопка «Копировать» и дата создания. При перезагрузке страницы, закрытии и повторном
открытии браузера User ID остаётся тем же, пока жива сессия (30 дней).

**Интерфейс.** Карточка «Ваш User ID» (`apps/web/src/components/identity-card.tsx`).

**Сервер.** `POST /session` создаёт личность и сессию одновременно; `GET /session` возвращает уже
существующую. Cookie `anonlink_session` — httpOnly, хранится только её SHA-256 хэш
(`apps/api/src/identity/*`).

**Данные.** Таблица `Identity` (публичный ID, даты, бан, политика заявок, добровольные данные о
себе и фильтры) и `Session` (хэш токена). Секрет сессии в открытом виде не хранится нигде.

**Безопасность.** User ID не даёт никаких прав: ни прочитать переписку, ни занять личность, ни
увидеть чужие настройки. Сессия восстанавливается только по cookie, которую нельзя прочитать из
JavaScript.

**Приёмка.** Интеграционные тесты `apps/api/test/rest.test.ts` (создание, восстановление, отзыв
сессии, cookie-атрибуты) и `apps/api/test/persistence.test.ts` (раздел «sessions and identities»);
браузерный тест «личность сохраняется после перезагрузки»
(`tests/e2e/specs/matching.spec.ts`); отдельный тест «сессию нельзя угнать, зная чужой User ID»
(`tests/e2e/specs/access.spec.ts`).

## 2. Смена личности («Новый ID»)

**Сценарий.** Человек хочет начать заново: например, его ID стал известен нежелательным людям.

**Ожидаемое поведение.** После подтверждения в диалоге все прошлые сессии отзываются, выдаётся
**новая** личность с новым User ID, открытые чаты закрываются. Прошлый ID перестаёт работать
сразу и восстановлению не подлежит — об этом сказано в тексте подтверждения.

**Интерфейс.** Кнопка «Новый ID» и диалог подтверждения в карточке User ID.

**Сервер.** `DELETE /session` отзывает все сессии личности и создаёт новую личность; каждому
подключённому устройству приходит `session:rotated`, после чего клиент переподключается с новой
cookie. Старой личности при этом ничего не переиспользуется.

**Данные.** Старые записи `Session` помечаются отозванными; новая личность — новая строка
`Identity`. Блокировки и жалобы остаются привязаны к **старой** личности (то есть смена ID не
является способом обойти блокировку со стороны того, кто вас заблокировал).

**Безопасность.** Смена доступна только владельцу cookie; чужой ID «увести» нельзя.

**Приёмка.** Интеграционный тест `DELETE /session` в `apps/api/test/rest.test.ts`; ручная проверка
диалога подтверждения.

## 3. Главный экран и разделы

**Сценарий.** Выбор, как искать собеседника.

**Ожидаемое поведение.** Всё на одной странице, без вкладок (`docs/DECISIONS.md` D22). Сверху —
строка User ID и индикатор соединения. Прямо под ней — поле поиска собеседника по User ID. Ниже —
кнопка «Найти собеседника» со случайным поиском, а под ней раскрывающийся раздел «Настройки». Внизу
страницы — «Связаться с администрацией». Во время поиска и во время чата поле поиска и настройки скрыты,
чтобы нельзя было уйти в сторону, оставив непонятное состояние. Свободное место по бокам страницы и
место под свёрнутыми настройками зарезервированы под будущую рекламу: области существуют и занимают
своё место, но пока пусты (`docs/DECISIONS.md` D23/D28).

**Интерфейс.** `apps/web/src/components/home-screen.tsx`, `identity-strip.tsx`, `direct-search.tsx`
(поиск по User ID), `search-panel.tsx` (кнопка поиска и ожидание), `settings-panel.tsx` (настройки),
`contact-owner-dialog.tsx`.

**Сервер.** Не участвует: экран — функция от состояния.

**Приёмка.** Браузерные тесты (все сценарии проходят через эту страницу).

## 4. Случайный поиск: запуск и отмена

**Сценарий.** «Найти собеседника» → ожидание → чат. Либо «Отменить поиск».

**Ожидаемое поведение.** После нажатия сразу видно состояние ожидания со счётчиком времени.
Повторные нажатия не создают вторую заявку на подбор. Отмена возвращает к выбору раздела; после
отмены можно **поменять настройки** и начать поиск заново.

**Интерфейс.** `apps/web/src/components/search-panel.tsx`.

**Сервер.** `match:join` ставит в очередь (повторный вызов — идемпотентен), `match:cancel` убирает.
Подбор выполняет сервер; клиент не решает, кто с кем встретится.

**Данные.** Очередь — только в памяти процесса. В базе не остаётся ничего о том, что человек искал.

**Безопасность.** Одновременно активна максимум одна очередь и один чат на личность.

**Приёмка.** Интеграционные тесты очереди (`apps/api/test/matching.test.ts`), браузерные тесты
«случайный подбор» и «отмена поиска» (`tests/e2e/specs/matching.spec.ts`).

## 5. Настройки поиска: данные о себе

**Сценарий.** «Настройки» → карточка «Что о вас знает поиск»: пол, год рождения, страна, город,
регион, языки общения.

**Ожидаемое поведение.** Все поля необязательные; можно ничего не указывать и искать. Пол — две
кнопки, «Женский» и «Мужской»; повторное нажатие на выбранную снимает выбор, то есть возвращает
«не указывать» (решение владельца от 2026-10-20: третья кнопка не нужна). Год рождения спрашивается
вместо возраста, чтобы значение не устаревало. Страна выбирается из готового списка 194 государств
ООН; в списке и на карточке она названа на своём языке («Deutschland», «Россия», «中国»), потому что
так её узнаёт человек, а сравнивается и хранится двухбуквенный код ISO 3166-1, поэтому «Германия»,
"Germany" и «Deutschland» — одна страна (`docs/DECISIONS.md` D30/D33). Пустое значение — «не указана».
Введённые значения возвращаются при перезагрузке.

**Интерфейс.** `apps/web/src/components/settings-panel.tsx`; названия подставляются из
`apps/web/src/lib/labels.ts`.

**Сервер.** `PATCH /me/settings` принимает `{profile}` и сохраняет только известные поля (лишние
поля отклоняются). Значения нормализуются: лишние пробелы, регистр и «ё/е» приводятся к одному
виду (`normalizePlace`), геокодирования нет.

**Данные.** 13 колонок в `Identity`: `declaredGender`, `declaredBirthYear`, `declaredCountry`,
`declaredCity`, `declaredRegion`, `declaredLanguages` и фильтры (`pref*`). Все — необязательные или
со значением по умолчанию, поэтому миграции были простым добавлением колонок без перезаписи таблицы.
Код страны проверяется по тому же сгенерированному списку, что и в браузере (`countrySchema`).

**Безопасность.** Эти данные **никогда** не возвращаются другому пользователю: `GET /users/:publicId`
отвечает только «существует / принимает заявки». В интерфейсе прямо написано, что данные не
проверяются и собеседнику не показываются. Отдельный интеграционный тест ищет текст сообщения по
всем текстовым колонкам базы и подтверждает, что на установке по умолчанию (архив выключен)
переписка не сохраняется.

**Приёмка.** `apps/api/test/search-filters.test.ts` (сохранение и возврат, отказ в неизвестных
полях, пустое значение недопустимо), `apps/api/test/persistence.test.ts` (состав колонок, отсутствие
«захватываемых» данных), модульные тесты нормализации (`packages/shared/src/preferences.test.ts`).

## 6. Настройки поиска: фильтры

**Сценарий.** «Настройки» → карточка «Кого искать»: пол (кнопка «Любой» + «Женский»/«Мужской»),
возраст «от—до», «где искать» (кнопка «Любой» + три списка — «Страны», «Города» и «Регионы»;
страну выбирают из готового списка, город и регион можно выбрать из подсказок или ввести своё,
в каждом списке можно указать несколько значений), общий язык, разрешение на смягчение.

**Ожидаемое поведение.** Внизу карточки показано «Будет применяться» — список фильтров в понятных
словах, обновляющийся по мере ввода. Невозможный набор (нижняя граница возраста больше верхней) не
отправляется: кнопка сохранения заблокирована и сказано, что именно не так. В строках со списком
есть явная кнопка «Любой»: это и есть нейтральное состояние (пустой список), а не отсутствие выбора.
Название места добавляется в список кнопкой «Добавить» или клавишей Enter, повтор того же названия
не дублируется, из списка название убирается нажатием на него. Введённое, но ещё не добавленное
название тоже сохраняется вместе с фильтрами — набранный текст не пропадает.

**Интерфейс.** Тот же компонент; проверка выполняется **теми же** схемами, что и на сервере, поэтому
браузер и сервер не могут разойтись в правилах.

**Сервер.** Фильтры сохраняются в `Identity` и попадают в кэш каталога сразу же — новый фильтр
начинает действовать немедленно, а не после переподключения. Частичное обновление фильтров
объединяется с уже сохранёнными значениями и проверяется целиком, поэтому «ageMin: 40» при
сохранённом «ageMax: 30» отклоняется, а сохранённые значения при этом не портятся.

**Данные.** `prefGenders`, `prefAgeMin`, `prefAgeMax`, `prefCountries`, `prefCities`, `prefRegions`,
`prefLanguages`, `prefRelax`. «Где искать» называет места, которые должны быть указаны у собеседника:
«Страны» сравниваются с его страной, «Города» — с его городом, «Регионы» — с его регионом, а все три
списка складываются («или»), поэтому «Казань» и «Татарстан» вместе шире, чем регион в одиночку
(человек, указавший только город, подходит по городу и не подходит по региону). Пустой список
означает «где угодно»; отдельного значения «любой» в данных нет (см. `docs/DECISIONS.md` D25/D27/D33).
Сравнение городов и регионов складывает регистр, лишние пробелы и «ё»/«е», но не угадывает географию:
«Спб» и «Санкт-Петербург» — разные названия. Страна сравнивается кодом ISO 3166-1, поэтому названия
на разных языках и написание в любом регистре — одно значение; код вне списка отклоняется.

**Безопасность.** Ограничений по возрасту нет — это решение владельца (см. «Противоречия», п. 2).
Границы «от—до» выбирает сам человек; сервер принимает любое значение, которое вообще может быть
возрастом. Пустой фильтр ничего не ограничивает; указанный фильтр ограничивает строго.

**Приёмка.** `apps/api/test/search-filters.test.ts` (инвертированный диапазон, значение, не являющееся
возрастом, неизвестный язык, неизвестная страна, неизвестное поле, «сохранённое не портится»,
совпадение по коду страны), модульные тесты `searchPreferencesSchema`/`countrySchema`, браузерный тест
«у каждой строки фильтров есть „Любой“, и он снимает фильтр» (включая страну) и «невозможный диапазон
отклоняется до отправки» (`tests/e2e/specs/filters.spec.ts`).

## 7. Фильтры действительно применяются сервером

**Сценарий.** Два человека с несовместимыми предпочтениями ищут одновременно.

**Ожидаемое поведение.** Они **не** встречаются. При этом каждый остаётся в очереди и может
встретить кого-то другого.

**Сервер.** Правило строгое и **взаимное**: подобрать могут только того, кто подходит вам, и только
если вы подходите ему. Значение, которое человек не указал, **не** считается подходящим: фильтр
«только женщины» не подберёт того, кто пол не указал. Это проверяется в момент подбора на сервере,
а не в браузере.

**Данные.** Расчёт не требует базы: сравнение идёт по уже загруженным фактам личности в памяти.

**Безопасность.** Совпадение невозможно «в обход» фильтра; несовместимая пара не может оказаться в
одном чате.

**Приёмка.** `apps/api/test/search-filters.test.ts` — семь сценариев: пол (фильтр действует, даже
если вторая сторона ничего не фильтрует), незаполненный пол, возраст по году рождения, место с
учётом нормализации, несколько выбранных мест («или»), общий язык, отсутствие самопроизвольного
смягчения. Модульные тесты правил —
`packages/shared/src/preferences.test.ts` (в том числе взаимность и строгость фильтров). Браузерный
тест: «фильтр удерживает двух ожидающих, пока его не уберут» (`tests/e2e/specs/filters.spec.ts`).

## 8. Смягчение фильтров (расширение поиска)

**Сценарий.** Человек ищет с фильтром «только женщины» и разрешением на смягчение. Подходящих нет.
Через 45 секунд сервер снимает один фильтр и сообщает об этом.

**Ожидаемое поведение.** Смягчение происходит **только** с разрешения человека, **по одному** фильтру,
**только** у него одного, и каждый шаг озвучивается: всплывающее сообщение «Ищем шире: снят фильтр
«пол»» и строка «Уже снято: пол» на экране поиска, которая остаётся видимой. Никакое совпадение
никогда не объявляется раньше, чем оно действительно состоялось.

**Интерфейс.** Переключатель «Разрешить снимать фильтры по одному» / «Ничего не снимать»;
на экране поиска — список применяемых фильтров **по данным сервера**, строка о том, через сколько
начнётся смягчение, и список уже снятых.

**Сервер.** Порядок смягчения задан: язык → место → возраст → пол. Время задаётся настройками
`MATCH_RELAX_AFTER_MS` (45 с) и `MATCH_RELAX_STEP_MS` (20 с). Смягчением занимается только служба
обслуживания, и только для тех, кто разрешил; после снятия фильтров человек немедленно пробует
подобрать пару заново.

**Данные.** Ничего не сохраняется: это состояние очереди в памяти.

**Безопасность.** Отключение (`MATCH_RELAX_AFTER_MS=0`) полностью выключает функцию. Смягчение не
затрагивает блокировки, баны и лимиты — они проверяются отдельно и всегда.

**Приёмка.** Модульные тесты «ступеней» (`packages/shared/src/preferences.test.ts`), интеграционный
тест «при выключенной политике ничего не смягчается и не объявляется»
(`apps/api/test/search-filters.test.ts`), **браузерный тест полного цикла**: фильтр держит пару,
затем происходит объявленное смягчение и встречается именно тот, кто раньше был исключён
(`tests/e2e/specs/filters.spec.ts`).

## 9. Экран поиска: критерии, время, отмена

**Ожидаемое поведение.** Видно: сколько времени идёт поиск, какие фильтры применяются **на самом
деле** (сервер сообщает их при постановке в очередь и при каждом смягчении), когда начнётся
смягчение. Если подбор идёт давно, ничего не «зависает»: счётчик продолжает идти, состояние не
теряется после перезагрузки страницы — фильтры и факт очереди восстанавливаются с сервера.

**Интерфейс.** `apps/web/src/components/search-panel.tsx`.

**Приёмка.** Браузерные тесты `tests/e2e/specs/filters.spec.ts` и `matching.spec.ts`.

## 10. Активный чат

**Сценарий.** Собеседник найден.

**Ожидаемое поведение.** Открывается переписка: псевдоним собеседника, время сообщений, поле ввода со
счётчиком «длина/максимум», кнопки «Отправить», «Следующий», «Завершить», а также «Пожаловаться» и
«Заблокировать». Сообщения доставляются в обе стороны сразу. Слишком длинное сообщение не
отправляется, а показывается, на сколько символов его нужно сократить.

**Интерфейс.** `apps/web/src/components/chat-panel.tsx`.

**Сервер.** `chat:message` требует, чтобы отправитель был участником именно этого чата; сообщения
дедуплицируются по `clientMessageId`, поэтому повторная отправка после обрыва связи не создаёт
дубликат. Текст обрезается и проверяется по длине; пустые и состоящие из пробелов сообщения
отклоняются.

**Данные.** Переписка по умолчанию **не сохраняется**: она живёт в памяти процесса, ограничена по
объёму и удаляется вместе с чатом. Исключение — архив владельца (§20): если он включён и охватывает
чат, те же сообщения дополнительно записываются в базу.

**Безопасность.** Собеседник в случайном чате не видит ваш User ID — только псевдоним. Посторонний,
знающий идентификатор чата, не может ни прочитать его, ни писать в него, ни завершить его, ни
заблокировать чужого собеседника (проверяется на сервере).

**Приёмка.** Интеграционные тесты чата и доступа (`apps/api/test/chat.test.ts` — доступ участника,
`apps/api/test/moderation.test.ts` — блокировка/жалоба только своего собеседника), браузерные тесты:
переписка в обе стороны, «третий лишний» (`tests/e2e/specs/access.spec.ts`), защита от двойного
подбора (`tests/e2e/specs/matching.spec.ts`).

## 11. Завершение чата и «Следующий»

**Ожидаемое поведение.** «Завершить» закрывает разговор с обеих сторон: у того, кто завершил,
причина честная («вы завершили чат»), у собеседника — «собеседник вышел» или «собеседник отключился».
«Следующий» завершает текущий чат и **сразу** ставит в очередь новый поиск.

**Сервер.** Состояние чата — только на сервере. Повторное завершение, «догоняющие» события или
запоздавшие команды не могут закрыть новый чат: клиент отбрасывает события для чата, которого у него
уже нет.

**Данные.** При завершении чата в базу пишется только счётчик сообщений (для статистики), не текст.

**Приёмка.** Интеграционные тесты жизненного цикла чата, браузерный тест «завершение и следующий
собеседник» (`tests/e2e/specs/matching.spec.ts`).

## 12. Обрыв связи и переподключение

**Ожидаемое поведение.** Потеря связи показывается как «соединение потеряно» и «ждём
восстановления», а не как выход человека. В течение 15 секунд чат сохраняется: после восстановления
соединения переписка и собеседник на месте. Если собеседник не вернулся — чат завершается с причиной
«собеседник отключился».

**Интерфейс.** Индикатор соединения (`apps/web/src/components/connection-badge.tsx`) и системные
сообщения в переписке.

**Сервер.** Разрыв соединения — не выход из чата. Если после перезапуска сервера чат всё же пропал,
клиент получает честный ответ `CHAT_NOT_FOUND` и не «зависает».

**Приёмка.** Интеграционный тест повторного подключения, браузерные тесты
(`tests/e2e/specs/resilience.spec.ts`), включая полный перезапуск API.

## 13. Прямой контакт по User ID

**Сценарий.** «По User ID» → ввод ID → «Проверить» → «Отправить заявку».

**Ожидаемое поведение.** Сначала проверка формата (в браузере, до обращения к серверу), потом поиск.
Возможные ответы: «пользователь не найден», «пользователь найден, но отключил заявки», «пользователь
найден и принимает заявки» — и только тогда кнопка отправки. У получателя появляется диалог с
заявкой и таймером; он принимает или отклоняет. Отправитель видит обратный отсчёт и результат.

**Интерфейс.** `apps/web/src/components/direct-panel.tsx`,
`apps/web/src/components/incoming-request-dialog.tsx`.

**Сервер.** Пять проверок перед отправкой: формат ID, существование, «не себе», доступность
(не в чате), политика заявок, отсутствие блокировки. Повторная отправка той же заявки не создаёт
вторую. Число ожидающих заявок у одного человека ограничено.

**Данные.** Заявки живут в памяти; в базе остаётся только политика входящих заявок. При истечении
или отказе ничего не сохраняется.

**Безопасность.** Поиск по ID ограничен по частоте, чтобы нельзя было перебором проверять
существование идентификаторов; «неизвестный, но правильный по формату ID» и «существующий» обрабатываются
одинаково по стоимости. Себе заявку отправить нельзя. **Осознанная плата за этот режим:** получатель
видит ваш User ID — об этом прямо написано над полем ввода, до нажатия кнопки.

**Приёмка.** Интеграционные тесты `apps/api/test/direct.test.ts` (отправка, все отказы, повтор, приём,
отказ), браузерные тесты `tests/e2e/specs/direct.spec.ts`, ошибки ввода —
`tests/e2e/specs/errors.spec.ts`.

## 14. Настройка входящих заявок

**Сценарий.** «Принимать заявки» / «Не принимать заявки».

**Ожидаемое поведение.** Переключатель сразу показывает новое состояние, значение сохраняется и
переживает перезагрузку. Случайный поиск работает в обоих случаях.

**Сервер.** `PATCH /me/settings {incomingRequests}`; проверка выполняется в момент отправки заявки,
а не в браузере. Ответ сервера — источник правды и для интерфейса.

**Приёмка.** Интеграционный тест политики заявок, браузерный тест «пользователь с выключенными
заявками и сохранение настройки после перезагрузки» (`tests/e2e/specs/direct.spec.ts`).

## 15. Блокировки

**Сценарий.** Администрация решает, существует ли действие «Заблокировать» (страница `/admin`,
раздел «Модерация»). Если оно включено — кнопка есть во время чата, а список заблокированных — внизу
главной страницы, справа от списка друзей.

**Ожидаемое поведение.** По умолчанию блокировка **выключена**: кнопки нет ни у кого, и сервер
отказывает в новой блокировке. Включённая блокировка завершает текущий чат и действует **и после
переподключения**: человек больше не встретится в случайном поиске и не сможет отправить заявку.
Блокировку можно снять в её списке внизу главной страницы.

**Выключение — не амнистия.** Ранее поставленные блокировки продолжают действовать, пока человек сам
их не снимет: список заблокированных виден и при выключенном действии, без отдельного уведомления о
политике — отсутствие кнопки в чате говорит само за себя. Пользователь не может включить или выключить
эту возможность сам — это политика платформы, а не его настройка.

**Сервер.** Блокировка хранится в базе (направленная: «я заблокировал его»). Служба подбора
проверяет блокировки в обе стороны при каждом подборе и при каждой заявке, поэтому переподключение
или смена соединения не даёт обойти блокировку. Политика платформы хранится в таблице
`PlatformPolicy` (одна строка `default`, отсутствие строки = выключено) и проверяется сервером при
каждой попытке блокировки (`docs/DECISIONS.md` D31).

**Данные.** Таблицы `Block` и `PlatformPolicy`; кто кого заблокировал, посторонним не раскрывается.
Блокировка собеседника удаляет и дружбу с ним — в той же транзакции (`docs/DECISIONS.md` D34).

**Безопасность.** Заблокировать самого себя нельзя (ошибка «нельзя выбрать себя»); нельзя
заблокировать того, кого нет (ответ не отличается по смыслу от обычного «не найден»). Блокировка
текущего собеседника возможна только внутри своего чата.

**Приёмка.** Интеграционные тесты блокировок и жалоб (`apps/api/test/moderation.test.ts`), политики
платформы (`apps/api/test/platform.test.ts`, `apps/api/test/unit/platform.test.ts`), включая обход
через переподключение (раздел «connection loss» в `apps/api/test/chat.test.ts`), браузерные тесты
положительной блокировки, списка внизу страницы и переключателя администрации
(`tests/e2e/specs/moderation.spec.ts`), отказа третьему лицу (`tests/e2e/specs/access.spec.ts`),
«кто кого заблокировал, третьим лицам не раскрывается» (`apps/api/test/rest.test.ts`).

## 16. Жалобы

**Сценарий.** «Пожаловаться» → выбор причины → отправка. Разбор — на странице `/admin`, раздел
«Модерация».

**Ожидаемое поведение.** Жалоба отправляется, чат завершается. Жалоба не остаётся без ответа в
системе: она сохраняется вместе с фрагментом переписки, попадает в список администрации и удаляется
по истечении срока хранения (по умолчанию 30 дней). Администрация видит причину, пояснение автора,
снимок последнего сообщения, оба User ID, время и срок хранения и отмечает состояние жалобы:
«открыта», «просмотрена», «приняты меры» или «отклонена».

**Сервер.** Причина жалобы проверяется по списку; текст жалобы ограничен по длине. Повторная
жалоба на тот же чат не создаёт вторую запись. Список для администрации отдаётся от новых к старым и
не содержит жалоб с истёкшим сроком хранения; менять можно только состояние жалобы — причина, текст
и снимок переписки неизменяемы.

**Данные.** Таблица `Report` (причина, состояние, время, фрагмент переписки, обе личности). Жалоба на
собеседника удаляет и дружбу с ним — в той же транзакции (`docs/DECISIONS.md` D34).

**Безопасность.** Жалоба не раскрывает собеседнику, кто на него пожаловался; жаловаться можно только
на своего собеседника. Список жалоб и смена состояния доступны только по ключу владельца: без ключа
эти маршруты отвечают отказом. Отдельных учётных записей модераторов пока нет, поэтому действие
нельзя приписать конкретному человеку (`docs/ROADMAP.md`).

**Приёмка.** Интеграционные тесты жалоб (`apps/api/test/moderation.test.ts`), включая список и смену
состояния через административный API, и проверка очистки по сроку хранения (раздел «reports» в
`apps/api/test/persistence.test.ts`), браузерный сценарий «жалоба появляется в `/admin` с причиной,
снимком сообщения и сохраняемым состоянием» (`tests/e2e/specs/moderation.spec.ts`).

## 17. Контакты, друзья и связь с администрацией — **готово**

**Что есть.** Блокировки, жалобы, **взаимные друзья по явному согласию внутри живого чата**, форма
«Связаться с администрацией» и **добровольное** раскрытие своего User ID собеседнику (человек сам
решает это сделать). Автоматического обмена контактами нет ни при каких условиях: случайный чат сам по
себе не создаёт постоянной связи.

**Друзья.** Во время активного чата любой участник может нажать «В друзья». Собеседник видит вопрос с
псевдонимом этого чата, временем до истечения (60 секунд) и кнопками «Принять»/«Отклонить». Только
после согласия обе стороны получают User ID друг друга и дату знакомства; до этого правило «не
раскрывать User ID случайного собеседника» продолжает действовать. Если собеседник в этот момент тоже
нажимает «В друзья», это считается согласием, а не второй заявкой. Отказ или истечение времени
закрывают возможность просить в этом чате снова. Заявка живёт только в памяти сервера, перезагрузка
страницы восстанавливает её из `session:ready`, а завершение чата её отменяет.

Список друзей находится внизу главной страницы под поиском по User ID, слева от списка
заблокированных: User ID, дата знакомства, кнопки «Написать» и «Удалить». Он не показывается в
`/admin`, не содержит переписки, псевдонимов, статуса «онлайн» и не создаёт уведомлений о входе. Если
друг открывает личный чат, кнопка сразу показывает «Вы друзья», а не предлагает добавить его повторно.
Удаление одностороннее и немедленное: второй человек видит, что контакт удалён, и его список
обновляется. Блокировка, жалоба и «Новый ID» удаляют дружбу (при блокировке и жалобе — в той же
транзакции, что и само действие; при смене ID — молча, потому что уведомление выдало бы смену личности).

**Связаться с администрацией.** Ссылка внизу страницы открывает форму: тема (жалоба, предложение,
ошибка в работе, реклама, сотрудничество, другое), текст до 2000 знаков и необязательная строка «как с
вами связаться» в свободной форме. Форма прямо говорит, что сообщение сохраняется, чтобы администрация
могла его прочитать и ответить, что User ID автора видит только администрация, и что сообщение
удаляется автоматически по истечении срока хранения (по умолчанию 180 дней). Ответ приходит не
автоматически, а по указанным контактам — если человек их оставил. Лимит: не больше 5 сообщений в
сутки от одной личности. Администрация читает и удаляет их на той же закрытой странице, где лежит
архив (`/admin`), — ключ открывает одно место, а не два. Там же, в разделе «Модерация», лежат жалобы и
переключатель блокировок (§15–16).

**Чего нет.** Заявок в друзья вне чата, постоянного «входящего ящика» заявок, истории переписки,
псевдонимов и статусов присутствия у друзей, автоматических уведомлений о том, что друг появился
онлайн. Повторный личный чат возможен только через обычную заявку по User ID; история прошлого чата
для этого не открывается. Это осознанные ограничения, а не недоделанные места
(`docs/DECISIONS.md` D34).

**Почему так.** Требование «никогда не раскрывать контакты автоматически» и «не смешивать случайный
чат с постоянными контактами» выполнено строго: связь появляется только после явного согласия обоих,
и только внутри уже существующего чата. Заявка вне чата была бы нежелательным сообщением, а постоянный
ящик заявок — тем же самым с большей поверхностью. Форма связи с администрацией — не переписка между
людьми: она не создаёт постоянных связей, ничего не раскрывает собеседнику и не требует, чтобы у
человека вообще был чат.

**Приёмка.** Интеграционные тесты дружбы (`apps/api/test/friends.test.ts`: принятие, отказ, повторная
заявка, ответ не тому адресату, чужая/несуществующая комната, отмена при завершении чата, восстановление
после перезагрузки, удаление, блокировка, жалоба, смена ID), правила заявок
(`apps/api/test/friend-requests.test.ts`: одно на чат, срок, закрытие чата) и браузерный сценарий
«заявка → согласие → список друзей → удаление» (`tests/e2e/specs/friends.spec.ts`). Тесты формы и
браузерный сценарий администрации остаются в `apps/api/test/owner-messages.test.ts` и
`tests/e2e/specs/contact-owner.spec.ts`.

## 18. Ограничения частоты и размеров

**Ожидаемое поведение.** Слишком частые действия получают понятный отказ («слишком много запросов,
попробуйте позже»), а не тихую потерю. На сообщения, создание сессий, поиск по User ID и заявки
действуют отдельные лимиты; одновременно открытых соединений на личность — не больше четырёх.

**Сервер.** Собственный ограничитель частоты (ведро токенов) на каждый вид действия; параметры
задаются настройками (`RATE_LIMIT_*`). Превышение лимита не записывается в базу — иначе лимит сам
стал бы способом накопить данные о человеке.

**Приёмка.** Модульные тесты ограничителя (`apps/api/test/unit/rate-limit.test.ts`) и проверка того,
что срабатывание лимита ничего не записывает в базу (`apps/api/test/persistence.test.ts`, раздел
«abuse protections are durable»).

## 19. Состояния: загрузка, пусто, ошибка, нет связи

**Ожидаемое поведение.** Каждое состояние выглядит и объясняется отдельно:

| Состояние | Что видит человек |
| --- | --- |
| Загрузка | Скелет карточки с подписью «Получаем ваш User ID» |
| Нет связи с сервером | «Нет связи с сервером», причина и кнопка «Повторить» |
| Доступ закрыт | «Доступ закрыт» (например, личность заблокирована администратором) |
| Несовпадение версии | Понятное сообщение вместо непонятных ошибок |
| Поиск никого не нашёл | Экран ожидания продолжает работать; при включённом смягчении — сообщение о снятии фильтра |
| Не найден User ID | «Пользователь с таким ID не найден» без подсказки, существует ли он на самом деле |
| Ошибка действия | Всплывающее сообщение с причиной; ничего не «залипает» в вечном ожидании |

**Приёмка.** Браузерные тесты (`tests/e2e/specs/errors.spec.ts`), а также проверки отсутствия
ошибок в консоли в каждом сценарии.

## 20. Хранение данных и политика

**Что хранится постоянно:** личность и её настройки (включая добровольные данные о себе и фильтры),
сессии (только хэши), блокировки, жалобы, **принятые дружбы (пара User ID и дата)**, события
безопасности и сообщения, отправленные через форму «Связаться с администрацией» (с автоматическим
удалением по сроку хранения).

**Что не хранится по умолчанию:** переписка, факт поиска, кто с кем общался, **заявки в друзья**
(они живут в памяти не дольше минуты и исчезают вместе с чатом). Переписка живёт в памяти процесса и
исчезает с завершением чата — это проверяется тестом, который ищет текст отправленного сообщения по
всем текстовым колонкам базы (`apps/api/test/persistence.test.ts`).

**Архив переписки — только у владельца, по умолчанию выключен.** По решению владельца (2026-10-19,
`docs/DECISIONS.md` D21) у сервиса есть архив, который владелец включает сам и настраивает вручную:

- **Кого записывать.** Всех; по параметрам (пол, возраст «от—до», города, регионы, языки — незаявленное
  значение не считается совпадением, как и в фильтрах поиска); или только выбранных пользователей по
  User ID. Достаточно участия одного человека из выбранных — сохраняется весь диалог, а не половина.
- **Что записывать.** Текст сообщений; типы вложений (изображения, видео, аудио, файлы) можно отметить
  заранее, но вложений в продукте пока нет, поэтому эти отметки ничего не сохраняют.
- **Сколько хранить.** Заданное число дней; `0` — хранить, пока владелец не удалит вручную.
- **Как выключить.** Выключатель действует сразу: каждое сообщение проверяется в момент отправки,
  поэтому после выключения новые сообщения не записываются. Уже сохранённое остаётся, пока не выйдет
  срок или владелец не удалит его. Задним числом ничего не записывается.

Пользователям об архиве **не сообщается**: из интерфейса удалены все фразы про «переписка не
сохраняется». Доступ есть только у владельца — по длинному ключу `ADMIN_TOKEN` из файла настроек
сервера, на отдельной странице `/admin`; без ключа эта страница и её API не существуют вовсе.
Важное следствие, которое владелец должен понимать: архив хранится в базе **открытым текстом**,
поэтому тот, кто получит доступ к базе, к её резервной копии или к ключу, прочитает сохранённое
(`docs/SECURITY.md` §13).

**Прочие административные настройки:** переключатель блокировки (по умолчанию выключен, `PlatformPolicy`),
сроки (`REPORT_RETENTION_DAYS`, `SESSION_RETENTION_DAYS`,
`SECURITY_EVENT_RETENTION_DAYS`, `OWNER_MESSAGE_RETENTION_DAYS`, срок хранения архива
`retentionDays`), лимиты (`RATE_LIMIT_*`) и хэширование IP/User-Agent (`ABUSE_HASH_SALT`, по
умолчанию выключено).

## 21. Мультимедиа — подготовлено, но не реализовано

Фото, видео, голосовые сообщения и файлы **не** входят в MVP и не имеют ни интерфейса, ни хранения.
Архитектурная подготовка: сообщение описывается структурой с типом содержимого, а не голой строкой;
ограничение длины и способ хранения не завязаны на текст. Этого достаточно, чтобы добавить вложения
позже, не переписывая чат, но недостаточно, чтобы считать функцию «почти сделанной».

## 22. Монетизация — только готовность

Ни рекламных блоков, ни платежей, ни «Premium» в интерфейсе нет и быть не должно, пока не работает
основной сценарий. Готовность выражается в том, что (а) интерфейс не строится на предположении «всё
бесплатно навсегда» и (б) лимиты и права проверяются на сервере, поэтому платные ограничения можно
добавить позже как серверное правило, а не как надпись в браузере. Три области под рекламу уже
существуют как реальные контейнеры: колонки по бокам, полоса под свёрнутыми настройками и фон
чата. Пока в них ничего нет, они пусты и не занимают внимания (`docs/DECISIONS.md` D23/D28).

## 23. Производительность и масштабирование — честная граница

- Один процесс: очередь подбора и активные чаты живут в памяти. **Нагрузочных испытаний не
  проводилось**, поэтому «выдерживает N пользователей» не утверждается нигде.
- Что уже сделано осознанно: лимиты на соединения и сообщения, регулярная уборка «зависших»
  состояний, ограниченный объём хранимой переписки в памяти, отсутствие тяжёлых запросов в горячем
  пути подбора (сравнение идёт по данным в памяти).
- Что потребуется для нескольких серверов: общая очередь и общее присутствие (Redis),
  «липкие» соединения или обмен событиями между процессами. Точка расширения указана в коде
  (`apps/api/src/chat/chat.matching.ts`), но сама реализация не сделана.

## Противоречия и открытые вопросы

Записаны **явно**, а не разрешены молча.

1. **Пол и возраст указываются самим человеком.** Требование «фильтры по полу и возрасту» и
   требование «не выдавать непроверенное за проверенное» противоречат друг другу по своей природе:
   проверить нечего, регистрации нет. Решение: данные считаются добровольным предпочтением для
   подбора, в интерфейсе прямо написано, что они не проверяются, а собеседнику не показываются
   вообще. Пол не выводится ни из чего и не запрашивается обходными путями.
2. **Несовершеннолетние.** Решение владельца (2026-10-19): возрастных ограничений нет — границы
   фильтра «от—до» определяют сами пользователи. Технической проверки возраста не существует (нет
   регистрации и документов), поэтому любой «порог» был бы только видимостью защиты. Последствие,
   записанное, а не скрытое: человек, указавший себя несовершеннолетним, может попасть в чат ко
   взрослому. Это решение продукта, а не пробел в коде.
3. **Архивы переписки.** Изначально был выбран принцип «не хранить». Решение владельца (2026-10-19)
   изменено: хранение переписки возможно, доступ — только у владельца, включается выборочно (для всех,
   по параметрам или для отдельных пользователей), пользователям об этом не сообщается. **Реализовано**
   (`docs/DECISIONS.md` D21): архив выключен по умолчанию, включается на странице `/admin`, срок
   задаётся вручную. Это осознанный отказ от прежней гарантии: теперь конфиденциальность переписки
   зависит от действия владельца, а не от устройства системы. Прежнее свойство (данных просто не
   существует) утрачено, и документация говорит об этом прямо, а не повторяет старую формулировку.
4. **Смягчение фильтров против ожиданий пользователя.** «Найди мне только женщин» + автоматическое
   снятие фильтра = встреча с тем, кого человек исключал. Поэтому смягчение: только по разрешению,
   только по одному фильтру, всегда с явным сообщением и с видимым списком «уже снято». Это не
   скрытая подмена, а явный компромисс, который пользователь контролирует.
5. **«Друзья и контакты» (этап F/G исходного задания)** реализованы как взаимные друзья по явному
   согласию внутри активного чата (`docs/DECISIONS.md` D34, §17). Постоянного ящика заявок, истории
   переписки и связей вне чата нет — это осознанная граница, а не недоделка. Автоматического
   раскрытия User ID по-прежнему не существует.
6. **Мультимедиа** исключено из MVP по требованию, отмечено как «подготовлено архитектурно».
7. **Мультисерверность** не заявлена: очередь в памяти одного процесса. Реализация Redis не входит
   в MVP и отмечена как следующий этап.

## 24. Язык интерфейса и перевод переписки

Интерфейс существует на трёх языках: русском, английском и китайском. Переключатель стоит рядом с
переключателем темы, каждый язык назван на самом себе — «Русский», «English», «中文» — потому что
человек ищет в списке знакомое написание, а не перевод. По умолчанию интерфейс **русский** независимо
от языка браузера: `Accept-Language` не учитывается. Выбор запоминается в cookie и `localStorage` и
переживает перезагрузку; `<html lang>` и заголовок вкладки меняются вместе с ним. Страница владельца
`/admin` всегда остаётся русской.

Переписку можно перевести обычным браузерным переводчиком (Chrome, Edge, Яндекс) независимо от языка
интерфейса: страница не запрещает перевод, `lang` в разметке совпадает с выбранным языком, а
предложения не разорваны вставками, которые переводчик принимает за отдельные фразы.

Намеренно не переводятся только три вещи, и это защита от порчи, а не недоделка: User ID (код, а не
слово), таймеры и счётчики (цифры, меняющиеся каждую секунду) и названия языков. Переписка помечена
как «язык неизвестен», поэтому переводчик определяет язык каждого сообщения сам, а направление
письма выбирается по первой букве — арабский и иврит не окажутся перевёрнутыми. Подсказки о
клавишах вынесены в видимый текст: атрибуты `placeholder` браузерные переводчики не переводят.

Ограничение названо честно: автоматической проверки браузерного переводчика не существует, в
`docs/TESTING.md` (§9) есть ручной чек-лист. Собственные переводы интерфейса проверяются
автоматически (`language.spec.ts`): русский по умолчанию, все три словаря, сохранение выбора после
перезагрузки, `<html lang>` и заголовок, русский `/admin`.

Список языков в профиле и в фильтре — все основные языки (76 кодов ISO 639-1), каждый назван на
самом себе: «Русский», "English", «中文», «Español». На проводе и в базе хранится код, а не название,
поэтому расширение списка не делает уже сохранённые данные недействительными и не требует миграции.
Страны готовятся так же: готовый список ISO 3166-1, название — на языке самой страны, сравнение — по
коду, чтобы «Германия» и «Deutschland» были одним значением.

## 25. Интеграция с соцсетями (VK, Telegram) — **план, не реализовано**

Владелец планирует использовать чат из соцсетей. Сейчас **никакого кода VK или Telegram в проекте
нет**, и это честно указано в `docs/ROADMAP.md`. Архитектура уже не мешает интеграции: все правила
подбора, чата, друзей, блокировок и жалоб находятся на сервере, REST и Socket.IO описаны стабильными
схемами, а публичный User ID не является пропуском. Будущий адаптер соцсети — это **клиент того же
сервера**, а не второй чат: он не получает свою базу, свою очередь или право обходить фильтры.

Возможны две формы. **Веб-приложение внутри мини-приложения** (VK Mini Apps, Telegram Mini App)
загружается с нашего HTTPS-домена и использует обычную сессию; платформенный адаптер отвечает только
за тему, кнопку «назад», системную кнопку «поделиться» и проверку запуска. **Серверный бот** (Telegram,
сообщество VK) принимает вебхуки, проверяет подпись платформы и вызывает те же серверные операции, что
и браузер. В обоих случаях аккаунт соцсети привязывается к анонимной личности только после
**серверной** проверки подписи/токена; браузер не может назвать себя чужим аккаунтом. Привязка —
добровольная, раскрывается человеку и может быть снята; без неё анонимный режим работает как сейчас.

Чего в текущем объёме нет: таблицы `ExternalIdentity`, входа по токену для iframe без cookie, глубоких
ссылок на User ID, уведомлений, публикации в соцсеть от имени человека, модерации соцсети и самих
адаптеров. Секреты `VK_*`/`TELEGRAM_*` не добавлены, потому что приложений и ключей ещё нет. Полный
чек-лист и отклонённые варианты — в `docs/INTEGRATIONS.md` и `docs/DECISIONS.md` D35. Никаких обещаний
«скоро заработает» интерфейс не даёт.
